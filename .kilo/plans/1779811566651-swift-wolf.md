# OAuth Login Support for AI Providers

## Overview
Add OAuth-based login as an alternative to manual API key entry for AI providers that support it. Users can click "Sign in with [Provider]" to authenticate via the provider's official OAuth flow, and the app securely stores access/refresh tokens in the macOS Keychain.

**Current State:** All 9 providers require manual API key copy-paste. API keys are stored as plain strings in `Profile` (serialized to disk). Only Claude Code CLI credentials touch the system Keychain.

## Provider OAuth Feasibility

| Provider | OAuth Feasible | Notes |
|----------|---------------|-------|
| **Claude/Anthropic** | Partial | No public OAuth for usage APIs. Claude Code CLI already has its own OAuth (handled by `ClaudeCodeSyncService`). We can improve auto-detection of CLI credentials but cannot add a standalone OAuth flow. |
| **OpenAI/Codex** | No | OpenAI OAuth is for building apps *on* OpenAI, not for reading usage/billing data. The usage dashboard APIs require API keys. OAuth tokens do not grant billing access. |
| **Google/Gemini** | Yes | Google OAuth 2.0 is fully supported. Scope `monitoring.read` grants Cloud Monitoring access for usage data. Requires Google Cloud OAuth client registration. |
| **GitHub/Copilot** | Yes | GitHub OAuth is fully supported. Scopes `read:user` + `read:org` grant profile and org-level Copilot usage access. Requires GitHub OAuth App registration. |
| **Kimi** | No | Moonshot AI does not offer OAuth for third-party usage tracking. |
| **DeepSeek** | No | DeepSeek does not offer OAuth for third-party usage tracking. |
| **GLM** | No | Zhipu AI does not offer OAuth for third-party usage tracking. |
| **Qwen** | No | Alibaba DashScope does not offer OAuth for third-party usage tracking. |
| **MiniMax** | No | MiniMax does not offer OAuth for third-party usage tracking. |

**Decision:** Implement OAuth for **Google/Gemini** and **GitHub/Copilot** only. All other providers remain API-key based.

## Architecture

### 1. Secure Token Storage (Keychain)

Create a new `OAuthTokenStore` service that uses the macOS Keychain to store access tokens, refresh tokens, and expiry dates per provider per profile.

```
Claude Usage/Shared/Services/OAuth/
├── OAuthTokenStore.swift           # Keychain CRUD for tokens
├── OAuthToken.swift                # Token model (accessToken, refreshToken, expiry, provider, profileId)
└── OAuthFlowCoordinator.swift      # Generic ASWebAuthenticationSession orchestrator
```

**Token model:**
```swift
struct OAuthToken: Codable {
    let provider: AIProvider
    let profileId: UUID
    var accessToken: String
    var refreshToken: String?
    var expiresAt: Date?
}
```

**Keychain keys:** `com.claudeusage.oauth.{provider}.{profileId}`

**Migration:** On first launch with new version, existing API keys in Profile remain untouched. OAuth is additive.

### 2. Generic OAuth Flow Coordinator

A reusable `OAuthFlowCoordinator` that uses `ASWebAuthenticationSession` to handle the PKCE-based OAuth flow:

1. Generate PKCE code verifier + challenge
2. Open `ASWebAuthenticationSession` with provider's authorize URL
3. Handle callback via custom URL scheme `claude-usage-tracker://oauth/callback`
4. Exchange authorization code for tokens (POST to token endpoint)
5. Store tokens in Keychain via `OAuthTokenStore`
6. Update Profile to mark provider as OAuth-connected

**URL Scheme Registration:** Add to `Info.plist`:
```xml
<key>CFBundleURLTypes</key>
<array>
  <dict>
    <key>CFBundleURLName</key>
    <string>com.claudeusage.oauth</string>
    <key>CFBundleURLSchemes</key>
    <array>
      <string>claude-usage-tracker</string>
    </array>
  </dict>
</array>
```

### 3. Provider-Specific OAuth Implementations

Each supported provider gets a config struct conforming to `OAuthProviderConfiguration`:

```swift
protocol OAuthProviderConfiguration {
    var authorizationEndpoint: URL { get }
    var tokenEndpoint: URL { get }
    var scopes: [String] { get }
    var clientId: String { get }
    var redirectUri: String { get }
}
```

**Google/Gemini config:**
- Authorization: `https://accounts.google.com/o/oauth2/v2/auth`
- Token: `https://oauth2.googleapis.com/token`
- Scopes: `["https://www.googleapis.com/auth/monitoring.read", "https://www.googleapis.com/auth/cloud-platform.read-only"]`
- Client ID: From Google Cloud Console (to be registered)
- Redirect: `com.claudeusage.app:/oauth/callback`

**GitHub/Copilot config:**
- Authorization: `https://github.com/login/oauth/authorize`
- Token: `https://github.com/login/oauth/access_token`
- Scopes: `["read:user", "read:org"]`
- Client ID: From GitHub OAuth App settings (to be registered)
- Redirect: `claude-usage-tracker://oauth/callback`

### 4. Token Refresh

Create `OAuthTokenRefresher` service that:
- Checks token expiry before each API call
- Uses refresh token to get new access token when expired
- Updates Keychain with new tokens
- Falls back to re-authentication if refresh fails

Google supports refresh tokens natively. GitHub OAuth apps do not automatically issue refresh tokens unless configured; may need to re-auth when token expires.

### 5. Service Layer Updates

Update the API service classes to support OAuth tokens:

**GeminiAPIService.swift:**
- Add OAuth token lookup path: if `geminiOAuthToken` exists in Keychain, use `Authorization: Bearer <token>` instead of `?key=<apiKey>`
- Cloud Monitoring API calls already accept OAuth Bearer tokens
- Keep `?key=<apiKey>` fallback for AI Studio API calls

**CopilotAPIService.swift:**
- Add OAuth token lookup path: if `copilotOAuthToken` exists in Keychain, use `Authorization: Bearer <token>` instead of the PAT
- GitHub API accepts OAuth tokens for `/user` and org endpoints
- Keep PAT fallback

### 6. UI Changes

**AIProvidersSettingsView.swift:**
- Each provider card now shows two options when tapped: "Sign in with [Provider]" and "Enter API Key Manually"
- OAuth-connected providers show the user's name/email (fetched from provider's user API) instead of "Connected"
- Add a "Disconnect" option that revokes tokens from Keychain

**New credential sheets:**
- `GeminiOAuthSheet` - Shows "Sign in with Google" button using `ASWebAuthenticationSession`
- `CopilotOAuthSheet` - Shows "Sign in with GitHub" button
- Existing API key sheets remain as "Enter manually" fallback

**New reusable components:**
- `OAuthSignInButton` - Branded sign-in button (Google blue, GitHub black)
- `OAuthDisconnectButton` - Revoke and clear tokens

### 7. Data Model Changes

**Profile.swift:**
- Add boolean flags to track OAuth connection state (for UI display):
  ```swift
  var geminiOAuthConnected: Bool = false
  var copilotOAuthConnected: Bool = false
  ```
- Do NOT store tokens in Profile (Keychain only)
- Update `hasGeminiCredentials` and `hasCopilotCredentials` computed properties to check both API key AND OAuth token presence

**AIProvider.swift:**
- Add `supportsOAuth: Bool` property
- Only `.gemini` and `.copilot` return `true`

### 8. Security Considerations

- **Client secrets:** Neither Google nor GitHub installed app OAuth requires a client secret when using PKCE. No secrets are bundled in the app.
- **Token storage:** All tokens in Keychain with `kSecAttrAccessibleWhenUnlockedThisDeviceOnly`
- **No plaintext:** API keys currently in Profile.plist remain for backwards compatibility; new OAuth tokens never touch Profile
- **State parameter:** All OAuth flows use cryptographically random `state` to prevent CSRF
- **PKCE:** Required for both Google and GitHub flows

### 9. Client Registration (External)

Before shipping, the app owner must register OAuth apps:

**Google Cloud Console:**
1. Create OAuth 2.0 client ID for "iOS" application type
2. Bundle ID: `com.claudeusage.app` (match app's bundle ID)
3. Scopes: Cloud Monitoring read-only
4. Download client ID (no secret needed for installed apps)

**GitHub OAuth Apps:**
1. Create new OAuth App at github.com/settings/developers
2. Authorization callback URL: `claude-usage-tracker://oauth/callback`
3. Enable "Device Flow" as fallback option
4. Scopes: `read:user`, `read:org`
5. Note client ID and client secret

These client IDs must be configured in the app's build settings (not hardcoded in source). Use `Info.plist` or Xcode build configuration.

## Implementation Phases

### Phase 1: Foundation
1. Create `OAuthToken` model and `OAuthTokenStore` (Keychain wrapper)
2. Add custom URL scheme to `Info.plist`
3. Create generic `OAuthFlowCoordinator` with PKCE support
4. Add `supportsOAuth` to `AIProvider`
5. Update `Profile` with OAuth connection flags

### Phase 2: Google/Gemini OAuth
1. Create `GoogleOAuthConfiguration`
2. Implement `GeminiOAuthSheet` UI
3. Update `GeminiAPIService` to use OAuth token when available
4. Add token refresh logic for Google
5. Test Cloud Monitoring API with OAuth token

### Phase 3: GitHub/Copilot OAuth
1. Create `GitHubOAuthConfiguration`
2. Implement `CopilotOAuthSheet` UI
3. Update `CopilotAPIService` to use OAuth token when available
4. Handle GitHub token expiration (no refresh token by default; may need re-auth prompt)
5. Test org-level Copilot usage with OAuth token

### Phase 4: Polish
1. Update `AIProvidersSettingsView` provider cards to show OAuth status
2. Add "Disconnect" functionality (clear Keychain + revoke via provider API)
3. Handle errors gracefully (network, user cancel, invalid token)
4. Add loading states during OAuth flow
5. Update localization strings

## Open Questions

1. **Client ID management:** Should client IDs be bundled in the app binary or fetched from a backend? Bundling is standard for installed apps but means the app cannot rotate IDs without an update.
2. **GitHub refresh tokens:** GitHub OAuth apps do not issue refresh tokens by default. Should we use a GitHub App instead (which supports refresh tokens)? GitHub Apps have a different auth model and may be overkill.
3. **Claude Code auto-detection:** Should we improve the existing `ClaudeCodeSyncService` to auto-detect and sync CLI OAuth credentials without requiring the user to manually trigger it? This would feel like "OAuth" for Claude even though it's not a true OAuth flow.
4. **Provider registration overhead:** Registering and maintaining OAuth apps with Google and GitHub requires ongoing compliance (privacy policy, terms of service). Is this acceptable for the app's business model?
